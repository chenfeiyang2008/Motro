# 实施与验收门禁

本文定义 Motro 每张开发工单从领取到本地提交的固定流程。目标是让快速交付建立在可复核事实之上，而不是以报告替代证据。

## 1. 进入工单

开始前必须：

1. 读取 `PRODUCT.md`、`CONTEXT.md`、相关 ADR、阶段 spec 和本工单；
2. 确认 `Blocked by` 中的工单均已验收并提交；
3. 记录基线提交哈希与 `git status --short --branch`；
4. 区分本工单文件、owner WIP、生成物和受保护目录；
5. 明确非范围、禁止依赖、禁止外部调用及是否允许 migration；
6. 把工单状态改为 `claimed`，但不得改写已应用 migration。

若任何依赖尚未提交，工单不得用“先写一点”绕过顺序。

## 2. 模块设计门

新增能力应形成深模块：调用方看到的接口小而稳定，复杂性留在模块内部。

- Controller 只处理协议、身份、DTO 与错误映射；业务事务留在 Service/Domain。
- Domain 暴露纯规则、确定性状态转换和稳定词汇，不依赖 Nest、数据库或浏览器。
- Repository/数据库边界集中 SQL 与锁语义，不向 UI 泄露存储键、物理路径或供应商秘密。
- Web 只消费版本化 API；不复制服务端校验、FSRS、权限或提交规则。
- 外部供应商必须经窄 adapter；测试使用 fixture/fake，普通测试不得联网。
- 业务事实与投影分离：不可变事实 append-only，派生读模型可重建。

评审时必须能回答：模块隐藏了什么复杂性、调用方最少需要知道什么、哪个测试直接验证该接口。

## 3. 数据与事务门

涉及写入时必须明确：

- 事务开始、加锁顺序、提交点和失败回滚范围；
- 幂等 scope、key、request hash、首次响应事实和并发行为；
- 数据库最终防线（FK、UNIQUE、CHECK、部分索引或触发器）；
- 不可变事实的 UPDATE/DELETE 行为；
- 资源归属与清理顺序；
- migration 只能追加，空库与增量库都要验证。

测试不得通过 `DISABLE TRIGGER`、`session_replication_role`、宽用户名匹配或共享库清库来获得通过。需要删除不可变测试事实时，使用一次性数据库或独立 Docker 卷整体销毁。

## 4. 实现门

- 先写能捕获失败语义的单元/集成测试，再完成实现；回归测试应在缺陷版上真实失败。
- 错误返回统一信封，区分 400/401/403/404/409/422/429/500，并保持 OpenAPI 一致。
- 日志、审计、API、生成物和测试报告不得包含密码、Token、密钥、存储路径或完整敏感 payload。
- 不在生产代码放环境变量测试后门；失败注入应位于测试适配器或一次性数据库层。
- 新依赖必须精确锁版本、核对许可证/维护状态/供应链风险，并说明为何标准库或既有依赖不足。
- 生成物只能由既定脚本产生，连续生成两次应无漂移。

## 5. UI 门

- 每页只有一个与当前状态匹配的主操作；未实现行为必须明确禁用或不出现。
- 服务端是权限、状态、时间、游标、解锁和幂等事实的唯一权威。
- 390/768/1440 px 无横向溢出；触控目标、键盘、语义标题、焦点、错误恢复完整。
- 支持 `prefers-reduced-motion`、更高对比度及不支持 `backdrop-filter` 的等价回退。
- Liquid Glass 只用于功能层/导航/短暂浮层；内容工作面保持清晰不透明。
- UI 技能只能按 [`../ui/skill-security.md`](../ui/skill-security.md) 使用，不能改写产品规范。

## 6. 验证门

按风险选择并记录实际执行结果，默认完整门禁为：

```bash
git diff --check
pnpm typecheck
pnpm lint
pnpm build
pnpm format:check
pnpm openapi:check
pnpm db:migrate:check
MOTRO_REQUIRE_DB=1 pnpm test
```

涉及浏览器时额外要求 Chromium + WebKit；涉及导入不可变事实时使用官方隔离 runner。跳过必须列出数量与技术原因，不能写成通过。

## 7. 审查门

重要或复杂工单至少进行两轴审查：

1. **Spec**：是否完整满足工单，是否偷换语义或混入下一票；
2. **Standards**：是否符合仓库安全、架构、测试、UI 与生成物规则。

P0/P1 必须修复并以新回归证据复审；P2 要么修复，要么记录明确理由与后续票。报告中的每项事实必须能在代码、SQL 或真实测试中定位。

## 8. 本地提交门

只有最终验收通过后才可提交：

1. `git diff --check`；
2. 只暂存批准清单；
3. `git diff --cached --check`；
4. `git diff --cached --stat` 和 `git diff --cached --name-only` 复核；
5. 创建一个语义明确的本地提交；
6. 报告提交哈希、文件统计和 `git status --short --branch`；
7. 未经明确授权不得 `git push`；
8. 提交后才能解锁下一工单。

治理文档、技能安装产物、原型和业务实现原则上分开提交，避免不可审计的大包。
